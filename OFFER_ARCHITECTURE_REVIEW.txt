1. PERFORMANCE PITFALLS AT SCALE (20k+ Products)
================================================================================

IDENTIFIED RISKS:

• JOIN EXPLOSION ON CATEGORY PAGES
  - Current: Each category query joins Product → OfferProduct → Offer
  - At 20k products with 5k active offers, this becomes expensive
  - Category page with 50 products = 50 subqueries for offers
  
  SUGGESTION: Pre-compute offer data into a Redis sorted set per category
  Key: "category:123:products_with_prices"
  Score: priority or price
  This eliminates DB joins entirely for listing pages

• CACHE INVALIDATION STORM
  - If one campaign has 500 products and gets updated, we must:
    - Update 500 hasActiveOffer flags
    - Invalidate 50+ category caches
    - Invalidate carousel cache
  - This creates write amplification
  
  SUGGESTION: Use lazy invalidation + soft TTL
  - Don't invalidate immediately on every change
  - Use stale-while-revalidate pattern
  - Background worker refreshes in batches

• CRON JOB BOTTLENECK AT SCALE
  - 1-minute cron checking all offers = fine at small scale
  - With 10k offers, each cron run scans entire offer table
  
  SUGGESTION: Use scheduled job queues instead
  - When offer created, schedule "activate" job for startDate
  - When offer created, schedule "deactivate" job for endDate
  - No polling needed (BullMQ, Quirrel, or Inngest)

• N+1 IN CART PRICE RECALCULATION
  - Cart has 10 items, each needs fresh offer lookup
  - That's 10 separate queries
  
  SUGGESTION: Batch query all cart product IDs at once
  WHERE productId IN (1, 2, 3, ...) with single join

2. DATABASE OPTIMIZATION ALTERNATIVES
================================================================================

MATERIALIZED VIEW (PostgreSQL)
------------------------------
CREATE MATERIALIZED VIEW product_effective_prices AS
SELECT 
  p.id,
  p.name,
  p.base_price,
  COALESCE(
    CASE 
      WHEN o.discount_type = 'PERCENTAGE' 
      THEN p.base_price * (1 - o.discount_value / 100)
      ELSE p.base_price - o.discount_value
    END,
    p.base_price
  ) as effective_price,
  o.id IS NOT NULL as has_offer
FROM product p
LEFT JOIN LATERAL (
  SELECT * FROM offer_product op
  JOIN offer o ON op.offer_id = o.id
  WHERE op.product_id = p.id
    AND o.is_active = true
    AND o.start_date <= NOW()
    AND o.end_date > NOW()
  ORDER BY o.priority DESC
  LIMIT 1
) o ON true;

CREATE INDEX idx_effective_prices_category ON product_effective_prices(category_id);

REFRESH MATERIALIZED VIEW CONCURRENTLY product_effective_prices;

PROS:
  • Queries become simple SELECTs (no joins)
  • Pre-computed effective prices
  • Indexed for fast lookups

CONS:
  • Need to refresh on offer/product changes
  • CONCURRENTLY requires unique index
  • Adds complexity to deployment

VERDICT: Consider for 50k+ products. Overkill for 20k.


GENERATED COLUMNS (PostgreSQL 12+)
----------------------------------
Not directly applicable here because effective_price depends on
another table (Offer). Generated columns only work with same-row data.


PARTIAL INDEXES
---------------
Current indexes are good, but add:

CREATE INDEX idx_active_featured_offers ON offer(priority DESC)
WHERE is_active = true AND is_featured = true AND start_date <= NOW() AND end_date > NOW();

This creates a tiny, focused index for carousel queries only.


BRIN INDEX FOR TIME RANGES
--------------------------
For offers table with many rows:

CREATE INDEX idx_offer_dates_brin ON offer USING BRIN(start_date, end_date);

BRIN indexes are tiny and perfect for time-series data.

3. SYNC STRATEGY EVALUATION
================================================================================

CURRENT APPROACH: hasActiveOffer flag + Middleware + Cron

CRITIQUE:

• FLAG IS REDUNDANT DATA
  - The "true" source of truth is: "Does an active offer exist for this product?"
  - hasActiveOffer is a cached version of this query
  - Every cached value creates sync risk
  
  QUESTION: Is the flag really necessary?

• ALTERNATIVE: QUERY-ONLY APPROACH (No Flag)
  
  Instead of:
    WHERE hasActiveOffer = true
    
  Use:
    WHERE id IN (
      SELECT product_id FROM offer_product op
      JOIN offer o ON op.offer_id = o.id
      WHERE o.is_active = true 
        AND o.start_date <= NOW() 
        AND o.end_date > NOW()
    )
  
  With proper indexes, this is fast enough for most scales.
  
  PROS:
    • No sync issues ever
    • No cron jobs for flag sync
    • Always accurate
  
  CONS:
    • Slightly slower queries
    • Can't filter products by "has discount" without subquery

• HYBRID SIMPLIFICATION
  
  Keep the flag, but simplify sync:
  
  INSTEAD OF: Middleware + Cron
  DO: Single background job triggered by:
      - Offer create/update/delete (immediate)
      - Hourly full-sync as safety net (not per-minute)
  
  The 1-minute cron is overkill. If offer starts at 12:00:00,
  a 5-minute delay is acceptable for most businesses.
  Flash sales can be handled by starting offers 5 min early.

• EVENT-DRIVEN ALTERNATIVE (More Elegant)
  
  Use database triggers + LISTEN/NOTIFY (PostgreSQL):
  
  1. Trigger on Offer insert/update/delete
  2. Trigger sends NOTIFY to application
  3. Application updates affected product flags
  4. No polling needed
  
  This is real-time with zero cron jobs.
  
  Implementation: pg-listen npm package
  
  PROS:
    • Instant updates
    • No cron overhead
    • Elegant, reactive
  
  CONS:
    • PostgreSQL-specific
    • Adds operational complexity
    • Connection must stay open

MY SUGGESTION:
  For your scale (20k products), keep the simple approach:
  - Middleware for immediate CRUD updates
  - 5-minute cron (not 1-minute) for time-based changes
  - Accept 5-min staleness for carousel/listings
  - Always query fresh for cart/checkout

OFFER STACKING RULES (Future Support)
-------------------------------------

Current: Priority field, highest wins, no stacking.

For future stacking support, consider:

• STACKING POLICY ENUM
  
  enum StackPolicy {
    EXCLUSIVE      // Cannot stack with other offers
    STACKABLE      // Can combine with others
    PRIMARY_ONLY   // Can be stacked ON, not WITH
  }

• STACKING CALCULATION ORDER
  
  1. Apply all PERCENTAGE offers first (multiplicative)
  2. Then apply FIXED_AMOUNT offers (additive)
  3. Cap at minimum price (e.g., $1) or max discount %

• STACKING LIMITS
  
  maxStackCount: 2  // Max 2 offers can stack
  
  This prevents "infinite discount" exploits.

• COMPATIBILITY RULES
  
  model OfferCompatibility {
    offerId1    Int
    offerId2    Int
    canStack    Boolean
    
    @@unique([offerId1, offerId2])
  }
  
  Explicit whitelist of which offers can combine.


FRONTEND PRICE HYDRATION & PARTIAL REVALIDATION
-----------------------------------------------

• PROBLEM: SSR renders price at build time, user sees stale price
  
  SOLUTION: Client-side hydration for prices
  
  1. SSR renders with cached price (fast initial load)
  2. Client fetches fresh price after mount
  3. If different, animate price update
  
  ```tsx
  function ProductCard({ product }) {
    const [price, setPrice] = useState(product.effectivePrice);
    
    useEffect(() => {
      fetch(`/api/products/${product.id}/price`)
        .then(res => res.json())
        .then(data => {
          if (data.effectivePrice !== price) {
            setPrice(data.effectivePrice);
          }
        });
    }, []);
    
    return <div className="price">{price}</div>;
  }
  ```
  
  This ensures SEO gets static HTML, users get fresh prices.

• PARTIAL REVALIDATION WITH TAGS
  
  Use Next.js cache tags for surgical invalidation:
  
  ```ts
  // When fetching
  fetch(url, { next: { tags: ['offers', `product-${id}`] } });
  
  // When offer changes
  revalidateTag('offers');  // Invalidates all offer-related caches
  revalidateTag(`product-${productId}`);  // Just one product
  ```
  
  This is more precise than revalidatePath.

• STREAMING SSR FOR DYNAMIC PRICES
  
  Use React Suspense to stream prices:
  
  ```tsx
  <Suspense fallback={<PriceSkeleton />}>
    <AsyncPrice productId={product.id} />
  </Suspense>
  ```
  
  Static content loads instantly, prices stream in.


FAILURE RECOVERY PATTERNS
-------------------------

• CIRCUIT BREAKER FOR OFFER SERVICE
  
  If offer queries fail repeatedly:
  - Fall back to base price
  - Log incident
  - Alert ops team
  - Auto-recover after 30 seconds
  
  Use: cockatiel or opossum npm packages

• REDIS CACHE FAILURE HANDLING
  
  ```ts
  async function getPrice(productId) {
    try {
      const cached = await redis.get(`price:${productId}`);
      if (cached) return JSON.parse(cached);
    } catch (e) {
      // Redis down, continue to DB
      logger.warn('Redis unavailable', e);
    }
    
    // Fallback to DB
    return await queryDatabase(productId);
  }
  ```
  
  Never let cache failure break the site.

• OFFER FLAG SELF-HEALING
  
  If hasActiveOffer gets out of sync:
  
  1. Daily job compares flag to actual offer status
  2. Logs discrepancies
  3. Auto-corrects
  4. Alerts if discrepancy rate > 1%

• IDEMPOTENT OFFER APPLICATION
  
  Cart should handle:
  - Offer applied twice (ignore duplicate)
  - Offer expired mid-session (recalculate)
  - Offer deleted while in cart (remove gracefully)
  
  Never crash, always show sensible fallback.

• DEAD LETTER QUEUE FOR FAILED SYNC
  
  If offer flag update fails:
  - Push to retry queue
  - Retry 3 times with backoff
  - After 3 failures, log and alert
  - Manual intervention required

5. SIMPLIFICATION OPPORTUNITIES
================================================================================

THINGS THAT MIGHT BE OVER-ENGINEERED:

• 1-MINUTE CRON
  Change to 5-minute. Nobody notices if sale starts 3 minutes late.
  If you need precision, use scheduled jobs (BullMQ).

• hasActiveOffer FLAG
  Consider removing entirely if:
  - You're not filtering products by "has discount"
  - Your offer queries are fast (< 10ms)
  - You have good caching
  
  The flag adds complexity for marginal query speed gain.

• PRICE LOCKING AT CHECKOUT
  This is important, but can be simplified:
  - Don't store snapshot in DB
  - Just re-query at payment time
  - If price changed, show modal: "Price updated, continue?"
  
  This is simpler than maintaining snapshot records.

• CAMPAIGN MODEL (for MVP)
  You can defer this entirely. Just add campaignId to Offer later.
  For now, use tags or naming conventions: "yalda-2024-*"


THINGS TO KEEP AS-IS:

• MANY-TO-MANY OFFER-PRODUCT
  Essential for bundle deals and bulk offers.

• PRIORITY FIELD
  Necessary for conflict resolution.

• REDIS CACHING FOR CAROUSEL
  Homepage is high-traffic. Cache is mandatory.

• FRESH QUERIES FOR CART/CHECKOUT
  Payment accuracy is non-negotiable.
