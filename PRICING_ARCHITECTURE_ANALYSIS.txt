================================================================================
          ANALYSIS: Should We Remove discountedPrice from Product?
                    Ice-Center E-commerce Architecture
                    Date: 2025-12-31
================================================================================


EXECUTIVE SUMMARY
=================

YES, removing discountedPrice from Product is a GOOD long-term decision.

The recommended approach is:
  - Product stores ONLY basePrice (original/list price)
  - All discounts live in the Offer model
  - Final price is calculated at query time
  - Use a "hasActiveOffer" flag for performance optimization

This creates a clean, maintainable architecture with a single source of truth
for pricing logic.


================================================================================
1. ANALYSIS: IS REMOVING discountedPrice A GOOD DECISION?
================================================================================

SHORT ANSWER: Yes, with proper implementation.

CURRENT STATE (ASSUMED):
------------------------
Product {
  basePrice:       Float    // Original price, e.g., 100,000 Toman
  discountedPrice: Float    // Sale price, e.g., 80,000 Toman
}

PROPOSED STATE:
---------------
Product {
  basePrice:       Float    // Only the original price
  // discountedPrice REMOVED
}

Offer {
  discountType:    PERCENTAGE | FIXED_AMOUNT
  discountValue:   Float
  startDate:       DateTime
  endDate:         DateTime
  products:        Product[]  // Many-to-many
}


WHY THIS IS A GOOD DECISION:
----------------------------

1. SINGLE SOURCE OF TRUTH
   - Currently: Discount info is scattered (Product.discountedPrice + Offer)
   - Proposed: All discounts live in Offer model only
   - Benefit: No conflicting data, easier debugging

2. TEMPORAL DISCOUNTS BECOME NATURAL
   - Offers have start/end dates
   - No need for cron jobs to update Product.discountedPrice
   - Expiry is automatic (query filters by date)

3. AUDIT TRAIL
   - Every discount is an Offer record
   - Can track: Who created it? When? What was the discount?
   - Product price history is preserved

4. FLEXIBILITY
   - Same product can have different offers over time
   - Bundle deals (buy 2 get 1) are easier
   - Flash sales, campaigns, user-specific offers all work the same way

5. REDUCED DATA INCONSISTENCY
   - No risk of discountedPrice > basePrice (invalid state)
   - No forgotten discounts lingering after promotion ends


================================================================================
2. PROS AND CONS: DISCOUNTS LIVING ONLY IN OFFER
================================================================================

PROS:
-----

✅ CLEAR SEPARATION OF CONCERNS
   Product = What the item IS (specs, images, base price)
   Offer = What promotions APPLY to it (discounts, timing)

✅ AUTOMATIC EXPIRY
   When endDate passes, offer simply doesn't match queries
   No background jobs needed to "reset" prices

✅ CAMPAIGN MANAGEMENT
   Group offers under campaigns (Yalda, Black Friday)
   Enable/disable entire campaigns at once

✅ CONSISTENT PRICING LOGIC
   One function calculates effective price everywhere
   Frontend, cart, checkout all use same logic

✅ EASY ROLLBACK
   Delete or disable an Offer = instant rollback
   No need to remember "what was the old price?"

✅ MULTIPLE CONCURRENT OFFERS
   Priority system handles conflicts
   Can have: Member discount + Seasonal sale (if you allow stacking)

✅ HISTORICAL ANALYSIS
   "How much discount did we give in December?"
   All data preserved in Offer records


CONS:
-----

❌ QUERY COMPLEXITY
   Need to join Product + Offer on every product fetch
   More complex SQL/Prisma queries

   MITIGATION: Optimize with indexes, caching, or denormalized flags

❌ PERFORMANCE OVERHEAD (SLIGHT)
   Runtime calculation vs. pre-computed value
   For category pages with 100 products, this adds ~5-10ms

   MITIGATION: Use Redis cache, ISR, or hasActiveOffer flag

❌ NO PERMANENT DISCOUNTS WITHOUT OFFER
   If you want a product to ALWAYS be 20% off, you need a "permanent" Offer
   (Offer with endDate far in future, e.g., 2099-12-31)

   MITIGATION: Create "Permanent Discount" offer type, or keep basePrice 
   as the already-discounted price for always-on-sale items

❌ ADMIN LEARNING CURVE
   Team must understand: "To discount a product, create an Offer"
   Can't just edit Product.price anymore

   MITIGATION: Good admin UX, clear documentation

❌ EDGE CASE: PRODUCTS WITHOUT OFFERS
   Products not in any Offer show basePrice only
   No "was/now" pricing unless you store listPrice separately

   MITIGATION: Keep listPrice field for MSRP/RRP reference

3. FETCHING CATEGORY LISTS WITH ACTIVE DISCOUNT INFO
================================================================================

THE CHALLENGE:
--------------
Category page shows 24 products. Each needs:
  - Name, image, basePrice
  - Is there an active offer? What's the effective price?

Without discountedPrice on Product, you need to JOIN with Offer.


SOLUTION A: JOIN QUERY (SIMPLE, SLIGHTLY SLOWER)
-------------------------------------------------

const products = await prisma.product.findMany({
  where: { categoryId: categoryId },
  include: {
    offerProducts: {
      where: {
        offer: {
          isActive: true,
          startDate: { lte: now },
          endDate: { gt: now }
        }
      },
      include: { offer: true },
      orderBy: { offer: { priority: 'desc' } },
      take: 1  // Only highest priority offer
    }
  }
});

// Then map to calculate effective price
const productsWithPrices = products.map(p => ({
  ...p,
  effectivePrice: p.offerProducts[0] 
    ? calculateDiscount(p.basePrice, p.offerProducts[0].offer)
    : p.basePrice,
  hasOffer: p.offerProducts.length > 0
}));

PROS: Simple, always accurate
CONS: Joins on every request


SOLUTION B: DENORMALIZED FLAG (RECOMMENDED)
-------------------------------------------

Add a computed/cached flag to Product:

Product {
  basePrice:      Float
  hasActiveOffer: Boolean  @default(false)  // Denormalized!
  activeOfferId:  Int?     // Optional: cache the current offer ID
}

Update this flag when:
  - Offer is created/updated/deleted
  - Offer starts (cron job at startDate)
  - Offer ends (cron job at endDate)

QUERY BECOMES SIMPLE:

const products = await prisma.product.findMany({
  where: { categoryId: categoryId },
  // No joins needed for list view!
});

// For detail view, still fetch full offer info
const productWithOffer = await prisma.product.findUnique({
  where: { id: productId },
  include: { offerProducts: { include: { offer: true } } }
});

PROS: Fast queries, simple frontend logic
CONS: Need to keep flag in sync (cron jobs or triggers)


SOLUTION C: REDIS VIEW CACHE (HYBRID)
-------------------------------------

Cache the entire category product list with pre-calculated prices:

Key: "category:electronics:products"
Value: [
  { id: 1, name: "Phone", basePrice: 100, effectivePrice: 80, hasOffer: true },
  { id: 2, name: "Tablet", basePrice: 200, effectivePrice: 200, hasOffer: false },
  ...
]
TTL: 5 minutes

Invalidate when:
  - Product in category is updated
  - Offer affecting category products changes

PROS: Extremely fast (no DB hit for cached requests)
CONS: Cache invalidation complexity, eventual consistency


SOLUTION D: DATABASE VIEW (POSTGRESQL)
--------------------------------------

Create a database view that pre-joins Product + Offer:

CREATE VIEW product_with_offers AS
SELECT 
  p.*,
  o.id as active_offer_id,
  CASE 
    WHEN o.discount_type = 'PERCENTAGE' 
    THEN p.base_price * (1 - o.discount_value / 100)
    ELSE p.base_price - o.discount_value
  END as effective_price,
  o.id IS NOT NULL as has_offer
FROM product p
LEFT JOIN offer_product op ON p.id = op.product_id
LEFT JOIN offer o ON op.offer_id = o.id
  AND o.is_active = true
  AND o.start_date <= NOW()
  AND o.end_date > NOW();

PROS: SQL does the work, Prisma can query the view
CONS: View maintenance, Prisma view support can be tricky


MY RECOMMENDATION: SOLUTION B (Denormalized Flag) + SOLUTION C (Redis Cache)
-----------------------------------------------------------------------------

1. Add hasActiveOffer flag to Product model
2. Update flag via Prisma middleware or event hooks when offers change
3. Cache category pages in Redis for 5 minutes
4. For product detail pages, always fetch fresh offer data

This gives you:
  - Fast list queries (filter by hasActiveOffer if needed)
  - Accurate pricing for detail/cart/checkout
  - Scalable to thousands of products

4. RECOMMENDED SCHEMA STRUCTURE
================================================================================

PRODUCT MODEL:
--------------
model Product {
  id              Int      @id @default(autoincrement())
  name            String
  slug            String   @unique
  
  // Pricing
  basePrice       Float    // The original/list price (never changes for offers)
  
  // OPTIONAL: Reference price for "was/now" display
  // Only needed if basePrice IS the discounted price for permanent sales
  msrp            Float?   // Manufacturer's Suggested Retail Price
  
  // Denormalized offer flag (for fast queries)
  hasActiveOffer  Boolean  @default(false)
  
  // Relations
  offerProducts   OfferProduct[]
  
  // ... other fields
  
  @@index([hasActiveOffer])
  @@index([categoryId, hasActiveOffer])
}


OFFER MODEL:
------------
model Offer {
  id              Int          @id @default(autoincrement())
  name            String
  slug            String?      @unique
  
  // Discount
  discountType    DiscountType
  discountValue   Float        
  maxDiscountCap  Float?       // For percentage: max Toman off
  
  // Timing
  startDate       DateTime
  endDate         DateTime
  
  // Control
  isActive        Boolean      @default(true)
  priority        Int          @default(0)
  
  // Display
  isFeatured      Boolean      @default(false)  // Show in carousel
  badgeText       String?      // "20% OFF", "Flash Sale"
  
  // Grouping
  campaignId      Int?
  campaign        Campaign?
  
  // Products
  products        OfferProduct[]
  
  @@index([isActive, startDate, endDate])
  @@index([isFeatured, isActive])
}

enum DiscountType {
  PERCENTAGE
  FIXED_AMOUNT
}


JUNCTION TABLE:
---------------
model OfferProduct {
  id                  Int      @id @default(autoincrement())
  offerId             Int
  offer               Offer    @relation(...)
  productId           Int
  product             Product  @relation(...)
  
  // Override for this specific product
  customDiscountValue Float?
  
  @@unique([offerId, productId])
  @@index([productId])
}

5. CACHING STRATEGY
================================================================================

LAYER 1: REDIS (APPLICATION CACHE)
----------------------------------
What to cache:
  - Homepage carousel offers (5 min TTL)
  - Category product lists with effective prices (5 min TTL)
  - Individual product details (10 min TTL)

Invalidation triggers:
  - Offer created/updated/deleted
  - Product added/removed from offer
  - Product price changed

Example:
  await redis.del(`category:${categoryId}:products`);
  await redis.del(`homepage:carousel`);


LAYER 2: ISR / STATIC GENERATION (NEXT.JS)
------------------------------------------
  // Category page
  export const revalidate = 300;  // 5 minutes
  
  // Product page
  export const revalidate = 600;  // 10 minutes
  
  // On-demand revalidation when offer changes:
  await revalidatePath(`/categories/${category.slug}`);
  await revalidatePath(`/products/${product.slug}`);


LAYER 3: CDN EDGE CACHE (ARVANCLOUD)
------------------------------------
  Cache-Control: public, s-maxage=300, stale-while-revalidate=600

Purge on offer changes (via Arvan API).

6. KEEPING hasActiveOffer FLAG IN SYNC
================================================================================

OPTION A: PRISMA MIDDLEWARE (RECOMMENDED)
-----------------------------------------

// prisma/middleware.ts
prisma.$use(async (params, next) => {
  const result = await next(params);
  
  // When OfferProduct is created
  if (params.model === 'OfferProduct' && params.action === 'create') {
    await updateProductOfferFlag(params.args.data.productId);
  }
  
  // When OfferProduct is deleted
  if (params.model === 'OfferProduct' && params.action === 'delete') {
    await updateProductOfferFlag(result.productId);
  }
  
  // When Offer is updated (isActive, dates)
  if (params.model === 'Offer' && ['update', 'delete'].includes(params.action)) {
    await updateAllProductFlags(result.id);
  }
  
  return result;
});

async function updateProductOfferFlag(productId: number) {
  const now = new Date();
  const hasOffer = await prisma.offerProduct.count({
    where: {
      productId,
      offer: {
        isActive: true,
        startDate: { lte: now },
        endDate: { gt: now }
      }
    }
  }) > 0;
  
  await prisma.product.update({
    where: { id: productId },
    data: { hasActiveOffer: hasOffer }
  });
}


OPTION B: CRON JOBS (FOR TIME-BASED UPDATES)
--------------------------------------------

Offers that START or END at scheduled times need cron jobs:

// Run every 5 minutes
async function syncOfferFlags() {
  const now = new Date();
  
  // Offers that just started
  const newlyActive = await prisma.offer.findMany({
    where: {
      isActive: true,
      startDate: { lte: now, gt: subMinutes(now, 5) }
    },
    include: { products: true }
  });
  
  // Offers that just ended
  const newlyExpired = await prisma.offer.findMany({
    where: {
      isActive: true,
      endDate: { lte: now, gt: subMinutes(now, 5) }
    },
    include: { products: true }
  });
  
  // Update affected products
  for (const offer of [...newlyActive, ...newlyExpired]) {
    for (const { productId } of offer.products) {
      await updateProductOfferFlag(productId);
    }
  }
}

7. POTENTIAL RISKS
================================================================================

RISK 1: DATA INCONSISTENCY
--------------------------
hasActiveOffer flag gets out of sync with actual offer status.

MITIGATION:
  - Run daily "full sync" cron job to verify all flags
  - Log discrepancies for debugging
  - Always use query-time check for critical paths (cart, checkout)


RISK 2: PERFORMANCE UNDER LOAD
-----------------------------
Category pages with 100+ products + offer joins = slow queries.

MITIGATION:
  - Proper indexes (see schema above)
  - Redis caching
  - Pagination (don't load 100 products at once)
  - Consider materialized views for very high traffic


RISK 3: ADMIN CONFUSION
-----------------------
Team used to editing Product.discountedPrice, now must create Offers.

MITIGATION:
  - Clear admin UX with "Quick Discount" button on product page
  - Good documentation
  - Validation: prevent weird states


RISK 4: PERMANENT DISCOUNTS
---------------------------
Some products are ALWAYS on sale. Without discountedPrice, how?

MITIGATION OPTIONS:
  a) Create "Permanent Offer" with endDate in 2099
  b) Use basePrice as the permanent sale price, msrp as original
  c) Add optional permanentDiscountPercent field to Product (hybrid)


RISK 5: MIGRATION COMPLEXITY
----------------------------
Converting existing discountedPrice data to Offers.

MITIGATION:
  - Write migration script to create Offers from current discounts
  - Run in staging first
  - Keep discountedPrice column for 30 days as backup (don't delete immediately)

8. ALTERNATIVE DESIGN PATTERNS
================================================================================

PATTERN A: PRICE HISTORY TABLE
------------------------------
Instead of Offers, track every price change:

model PriceChange {
  id          Int
  productId   Int
  oldPrice    Float
  newPrice    Float
  reason      String     // "Offer: Yalda Sale", "Manual adjustment"
  startDate   DateTime
  endDate     DateTime?  // null = current price
}

PROS: Full audit trail, can reconstruct any historical price
CONS: Complex queries, doesn't capture offer metadata


PATTERN B: COMPUTED COLUMN (DATABASE LEVEL)
-------------------------------------------
Use PostgreSQL generated columns:

ALTER TABLE product ADD COLUMN effective_price FLOAT 
  GENERATED ALWAYS AS (
    SELECT COALESCE(
      (SELECT calculate_offer_price(base_price, offer_id) 
       FROM active_offers WHERE product_id = id LIMIT 1),
      base_price
    )
  ) STORED;

PROS: DB handles computation, always in sync
CONS: PostgreSQL-specific, complex function maintenance


PATTERN C: EVENT SOURCING
-------------------------
Every price/offer change is an event:

ProductCreated { basePrice: 100 }
OfferApplied { offerId: 1, discount: 20% }
OfferExpired { offerId: 1 }
PriceChanged { newBasePrice: 90 }

Current price = replay all events.

PROS: Perfect audit trail, time-travel queries
CONS: Overkill for most e-commerce sites, complex implementation


================================================================================
9. FINAL RECOMMENDATION
================================================================================

DO THIS:
--------
1. REMOVE discountedPrice from Product model

2. ADD hasActiveOffer flag for fast queries

3. KEEP basePrice as the true original price

4. CREATE Offer model with:
   - discountType (PERCENTAGE, FIXED_AMOUNT)
   - discountValue
   - startDate, endDate
   - priority (for conflicts)
   - Many-to-many relation to Products

5. IMPLEMENT flag sync via:
   - Prisma middleware (for create/update/delete)
   - Cron job every 5 mins (for time-based start/end)

6. CACHE aggressively:
   - Redis for category lists (5 min)
   - ISR for pages (5-10 min)
   - CDN for API responses

7. FOR PERMANENT DISCOUNTS:
   - Create "evergreen" offers with far-future endDate
   - OR keep those items' basePrice as the actual sale price

8. CALCULATE effective price at query time:
   - Use helper function everywhere
   - Never trust cached prices for cart/checkout (fetch fresh)


WHY THIS WORKS:
---------------
- Single source of truth for discounts (Offer model)
- Automatic expiry (no cron needed to "reset" prices)
- Audit trail (every discount is a record)
- Flexible (campaigns, bundles, user tiers all possible)
- Performant (with caching + denormalized flag)
- Maintainable (clear separation of concerns)
